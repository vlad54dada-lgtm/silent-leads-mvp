# Silent Leads Retouch MVP

Офлайн-інструмент, який обробляє контрольну вигрузку silent-лідів з CRM, перевіряє строк першого
повторного касання, аналізує історію спілкування і формує рішення **для перевірки людиною**.
Реальні повідомлення не надсилаються, до CRM нічого не підключається, дані нікуди не передаються.

- План демо на 30 хвилин — [docs/demo-plan.md](docs/demo-plan.md), наступні кроки після MVP —
  [docs/next-steps.md](docs/next-steps.md)
- Що будуємо і навіщо — [PRODUCT.md](PRODUCT.md)
- Як будуємо (стек, правила, команди) — [CLAUDE.md](CLAUDE.md)
- Обмеження, припущення, наступні кроки — [docs/limitations.md](docs/limitations.md)
- Журнал перегляду кейсів з координатором — [docs/review-log.md](docs/review-log.md)
- Паспорт інструмента простими словами (логіка, рішення, перевірки, вартість) — [docs/passport.md](docs/passport.md)

  дані вигрузки і передаються замовнику окремо разом із вхідним файлом

## Запуск

Потрібні Python 3.12+ і [uv](https://docs.astral.sh/uv/). Інтернет після `uv sync` не потрібен.

```bash
uv sync
```

1. Покладіть вигрузку (Google Sheets → Файл → Завантажити → .xlsx) у `data/input/export.xlsx`.
   Папка `data/` не комітиться.
2. Скопіюйте `config.example.yaml` у `config.yaml` і за потреби змініть строк, зону, шаблони, фрази.
   Секретів у конфігу немає.
3. Перевірте файл:

```bash
uv run python -m silent_leads.cli validate --input data/input/export.xlsx --config config.yaml
```

4. Запустіть повний прогін:

```bash
uv run python -m silent_leads.cli run --input data/input/export.xlsx --config config.yaml --output data/output
```

Повторний запуск з тим самим файлом і конфігом повністю перезаписує `data/output/` і дає
побайтово ідентичний результат — дублікатів не буває.

### Результати в `data/output/`

| Файл | Зміст |
|---|---|
| `results.xlsx` | Аркуш «Результат»: `case_id, decision, reason, evidence_message_ids, draft_sms, template_status, reviewer_note` — рівно як у вигрузці. Аркуш «Проблеми даних» |
| `results.csv` | Те саме у CSV (UTF-8 з BOM, відкривається в Excel) |
| `data_issues.csv` | Усі знайдені проблеми даних: рівень, код, кейс, повідомлення, опис |
| `ai_labels.csv` | Лише `policy: v1`. Один рядок на кейс: мітка й впевненість AI, докази, пояснення + порожні `human_label` / `human_comment` для розмітки людиною |
| `labels.csv` + аркуш «Мітки» | Лише `policy: v2`. Мітка кейсу у форматі вкладки «Розмітка»: `label, reason, evidence_message_ids, question_for_owner, new_contact_after_silent` + впевненість, позиція клієнта, фінальне рішення, пояснення |
| `drafts.csv` + аркуш «Чернетки SMS» | Лише `policy: v2` з `drafts.enabled`. Чернетка SMS від AI для кожного `contact_candidate`, статус `ai_draft` / `ai_draft_rejected` / `ai_error`. Підказка сейлзу, не затверджений шаблон |
| `summary.md` / `summary.json` | Зведення: контрольна дата, кількість по кожному рішенню, кейси на ручну перевірку, знахідки, підсумок AI-аналізу, помилки даних |

Коди виходу: `0` — ок, `2` — файл не схожий на вигрузку (немає вкладки/колонки),
`3` — контрольні суми вкладки «Контроль» не збігаються, `4` — не визначено дату знімка,
`5` — команда `ai-eval` або `policy-eval` викликана з вимкненим AI.

### Windows з Application Control

Якщо політика безпеки блокує Python, який встановлює `uv`, і `.exe`-обгортки в `.venv\Scripts`,
створюйте середовище із системного Python і запускайте все через `python -m`:

```bash
export UV_PYTHON_PREFERENCE=only-system UV_PYTHON="C:/шлях/до/системного/python.exe" PYTHONUTF8=1
```

Далі ті самі команди з `uv run --no-sync python -m ...`. `scripts/run.ps1` запускає через готове `.venv`,
підхоплює ключ AI зі змінних користувача і перед прогоном явно пише,
чи увімкнено AI в конфігу і куди підуть дані.

## Як приймається рішення

1. **Дані.** Кожне погане значення — явна проблема (`data_issues.csv`), а не вигаданий дефолт.
   Помилка рівня `error` по кейсу → `manual_review`.
2. **Строк.** `silent_since_crm` → календарна дата в зоні CRM; контрольна дата — зі знімка
   (вкладка «Інструкція» → «Знімок UTC»), не з часу запуску. Касання дозволене, якщо минуло
   `>= first_touch_delay_days` днів (7 — тестове правило).
3. **Офіційна відписка — правилом.** Якщо все повідомлення клієнта — одне слово `STOP` або `UNSUBSCRIBE`
   (список `phrases.exact_opt_out`, регістр і крайня пунктуація не важливі) → `do_not_contact` незалежно від
   строку й контексту. «STOP» усередині фрази («stop by», «Reply STOP to opt out») правилом не є.
4. **Решта — за контекстом.** Усе інше, що написав клієнт, оцінює AI-аналіз діалогу (розділ нижче): відписка
   іншими словами, негатив, «так» у відповідь на пропозицію більше не писати. Фрази зі списку `phrases.hints`
   — лише підказка: з увімкненим AI вирішує модель, без нього кейс іде на ручну перевірку.
5. **Рішення** з пріоритетом `do_not_contact` > `manual_review` > `skip_not_due` > `contact_candidate`.
   На `manual_review` відправляють: подія після silent, приховане вхідне повідомлення, вхідна подія
   без читабельного тексту (дзвінок без транскрипту), репліка з невизначеним автором, відсутність
   будь-якого тексту від клієнта, помилки даних, а також будь-який невпевнений чи неоднозначний висновок AI
   або висновок по обрізаному діалогу (усе вмикається в `review:`). `--config` обовʼязковий: без нього
   списки фраз були б порожні.
6. **Текст** формується лише для `contact_candidate` і лише з наданого шаблону; без шаблону —
   порожній текст і `template_missing`.

## AI-аналіз контексту (опційно, погоджено з координатором)

Увімкнення в `config.yaml`:

```yaml
ai_review:
  enabled: true
  model: claude-sonnet-5-5   # рекомендована; Haiku 5.5 дешевша у 20 разів, але частіше відправляє на ручну перевірку
```

Ключ API читається зі змінної середовища, назву якої задає `ai_review.api_key_env`
(за замовчуванням `ANTHROPIC_API_KEY`); у конфіг або репозиторій ключ не класти. Змінну можна задати у файлі
`.env` поруч із проєктом (зразок — `.env.example`; файл у git не потрапляє): CLI читає його на старті, а змінна,
вже задана в середовищі, має пріоритет. Готовий конфіг для запуску через OpenRouter з чернетками —
`config.demo.yaml`.
На Windows зручно задати його один раз для користувача і запускати через `scripts/run.ps1`,
який підхоплює його автоматично:

```bash
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/run.ps1
```

Якщо ключа немає, прогін не падає: кожен кейс, який мала перевірити модель, отримує `manual_review`
з приміткою про невиконану перевірку (неперевірений кейс не є кандидатом).

Як працює: модель отримує діалог кейсу (репліки клієнта і сейлза в порядку часу, приховані повідомлення
позначені; без імен, дат і квот) і повертає мітку наміру клієнта `none / opt_out / negative / unclear`,
впевненість `high / medium / low`, ID повідомлень-доказів і пояснення. Далі діють правила:

| Відповідь моделі | Результат |
|---|---|
| `opt_out` або `negative`, впевненість `high`, є доказ із цього кейсу | `do_not_contact` |
| `none`, впевненість `high` | кейс проходить далі за строком → `contact_candidate` або `skip_not_due` |
| усе інше: `unclear`, `medium`/`low`, без доказу, помилка виклику | `manual_review` |

Модель ніколи не робить кейс кандидатом сама: строк, події після silent, приховані тексти й помилки даних
перевіряються окремо. Деталі й обмеження — у [docs/limitations.md](docs/limitations.md).

Замість прямого доступу до Anthropic можна використати Anthropic-сумісний шлюз, наприклад OpenRouter
(це додає посередника, який бачить тексти клієнтів, тож потребує окремого погодження):

```yaml
ai_review:
  enabled: true
  model: anthropic/claude-sonnet-5.5    # назва моделі як на openrouter.ai/models
  base_url: https://openrouter.ai/api
  api_key_env: OPENROUTER_API_KEY
```

Якщо шлюз не приймає структурований формат відповіді, інструмент повторює запит у режимі «лише JSON»
і перевіряє відповідь за тією самою схемою; будь-яка невідповідність → `manual_review`.

## Політика v2 «Кому пишемо» (друга частина спринту)

`policy: v2` у конфігу (так у `config.example.yaml`). Питання до кейсу одне: чи доречно писати клієнту ще раз.
Повний опис — [PRODUCT.md](PRODUCT.md) §11.

1. **Код без моделі:** точний STOP без подальших слів клієнта → `do_not_contact`; клієнт нічого не писав →
   `contact_ok` (просто замовк).
2. **AI** (`ai_review.enabled: true`) читає діалог і повертає мітку `contact_ok` / `do_not_contact` / `need_human`,
   причину, впевненість, докази та `message_id` останньої позиції клієнта. Він відрізняє «дорого» від «найняв
   інших», перенесення візиту від скасування проєкту, автовідповідач від відповіді.
3. **Код** перевіряє крок 4: прихована розмова або дзвінок без транскрипту після позиції клієнта → `need_human`.
   Далі строк 7 днів і новий контакт після silent дають фінальне рішення.
4. **Чернетки** (`drafts.enabled: true`): для кожного `contact_candidate` AI пише SMS-продовження діалогу.
   Код відхиляє текст із цифрами, цінами, посиланнями чи маскуванням. Чернетку перевіряє й надсилає сейлз.

Без AI v2 лишає людині всі кейси, де є слова клієнта: зміст діалогу правилами не оцінюється.

**Менше ручних перевірок.** За ТЗ будь-яка подія після `silent_since_crm` відправляє лід на `manual_review`.
Параметр `contact_policy.sales_followup_grace_hours` (наприклад 3) перестає вважати новим контактом дію продавця
без відповіді в межах цього вікна. На ручній перевірці лишаються, і це перевіряє код, а не модель: подія, яка не є
вихідною з роллю sales; розмова з клієнтом (більше ніж `followup_max_client_lines` реплік, які можуть належати
клієнту); репліка з невизначеним автором; позиція клієнта після silent; пізня дія продавця. У вигрузці v2 це
зменшує ручні перевірки з 44 до 21 зі 150 (14 %). З 2026-11-12 це значення за
замовчуванням (погоджено координатором); `null` повертає буквальне правило першого ТЗ.

**Кеш і вартість.** Відповіді моделі зберігаються в `ai_review.cache_dir` (за замовчуванням `data/ai_cache`).
Повторний прогін бере їх із кешу: не платить двічі, дає той самий результат і продовжує обірваний прогін з
того місця, де він зупинився. Якщо у шлюзу закінчились кошти або ліміт ключа, неоцінені кейси йдуть на
`manual_review`, а у виводі зʼявляється попередження з типом помилки: поповніть баланс і запустіть ту саму
команду ще раз. Діалог передається моделі компактним текстом (заголовок події + репліки), чернетка бачить
лише кінець діалогу (`drafts.context_chars`).

```bash
uv run python -m silent_leads.cli run --input data/input/export.xlsx --config config.yaml --output data/output
uv run python -m silent_leads.cli evaluate-policy-labels --input data/input/export.xlsx --config config.yaml --labels data/output/labels.csv --output data/output
uv run python -m silent_leads.cli policy-eval --config config.yaml --output data/output
```

`evaluate-policy-labels` порівнює `labels.csv` з еталоном у самій вигрузці (вкладки «Розмітка» і «Приклади») і
пише `policy_evaluation.md`: точність по мітках, матрицю, пропущені відмови (ціль — нуль) і хибні відмови.
`policy-eval` проганяє промпт на синтетичних діалогах [evals/policy_cases.yaml](evals/policy_cases.yaml).
Кейс із `not_candidate: true` — межовий: мітка може бути `contact_ok`, але дозвіл із високою впевненістю рахується
помилкою, бо такий лід не має ставати кандидатом.

## Валідація AI (v1): розмітка людиною і метрики

1. Після `run` відкрийте `data/output/ai_labels.csv`, у колонку `human_label` впишіть свою мітку для кожного
   кейсу (`none`, `opt_out`, `negative`, `unclear`), за бажання — коментар у `human_comment`.
2. Порівняйте:

```bash
uv run python -m silent_leads.cli evaluate-labels --labels data/output/ai_labels.csv --output data/output
```

У `evaluation.md` / `evaluation.json`: точність по 4 мітках, точність на рівні рішення (відмова / не відмова),
пропущені та хибні відмови, матриця невідповідностей, точність за рівнем впевненості, розбір кожної розбіжності
з поясненням моделі. У реальній вигрузці явних відписок може не бути, тому промпт додатково перевіряється на
синтетичних діалогах з відомими мітками ([evals/context_cases.yaml](evals/context_cases.yaml)):

```bash
uv run python -m silent_leads.cli ai-eval --config config.yaml --output data/output
```

Результат — `ai_eval.md` / `ai_eval.json` з тими самими метриками. Додавайте нові синтетичні кейси після
кожної знайденої помилки; жодного рядка з реальної вигрузки в цей файл копіювати не можна.

## Перевірка якості

```bash
uv run python -m pytest
uv run python -m ruff check . && uv run python -m ruff format --check .
uv run python -m mypy
```

Тести працюють лише на синтетичних даних і покривають: строк (до/в день/після, межа дня в зоні CRM),
точне правило STOP/UNSUBSCRIBE і його межі («stop by», сейлз, транскрипт), підказки без AI, усі гілки
відповіді моделі (блокує / пропускає / на ручну / помилка), авторство в транскриптах, відсутні/некоректні
дані, обидві гілки квоти, повторний запуск (побайтове порівняння), метрики валідації, CLI; для v2 — усі гілки
політики «Кому пишемо», крок 4, виняток STOP, жорсткі обмеження чернеток, оцінювання проти еталону.
